# تقرير تدقيق CSP وواجهات API والأمن

**التاريخ:** 12 سبتمبر 2026

**النطاق:** مستودع `kdamfleet-hue/Invoice-Bin-zoma-main` والنسخة المنشورة على `https://invoice-bin-zoma.509.rip`.

## الملخص التنفيذي

تم تحديد سبب تحذيرات `style-src` في سجلات 509.rip: التطبيق يستخدم عددًا كبيرًا من كتل `<style>` وخصائص `style="..."` داخل القوالب، بينما كانت سياسة CSP تسمح بمصادر CSS الخارجية فقط. تم تعديل تعريف السياسة في `app.py` لإضافة توجيهات CSS صريحة متوافقة مع الوضع الحالي، مع إبقاء السياسة في وضع **Report-Only**. لم يتم دفع التعديل أو نشره إلى 509.rip خلال هذا الفحص؛ لذلك يحتاج الإصلاح إلى commit ثم نشر يدوي/تكامل 509 قبل التحقق من انخفاض التحذيرات.

كما تم قياس نقاط API العامة دون مصادقة ثلاث مرات لكل نقطة. نقطة `/health` متاحة وتعيد `200`، بينما تحمي نقاط النظام بإرجاع `401`، وتعيد `/system_health` إعادة توجيه `302` إلى تسجيل الدخول، أما `/api/health` فغير موجودة وتعيد `404`.

## إصلاح CSP

### التغيير

تم تعديل `app.py` في تعريف `CSP_REPORT_ONLY` لإضافة:

```text
style-src ... 'unsafe-inline'
style-src-elem ... 'unsafe-inline'
style-src-attr 'unsafe-inline'
```

الاستثناءات مؤقتة ومحددة بـ CSS فقط؛ لم تتم إضافة `unsafe-inline` إلى `script-src`. السبب أن القوالب الحالية تحتوي على كتل CSS مضمّنة وخصائص `style` كثيرة، مثل `templates/base.html` و`templates/index.html` و`templates/alerts.html` وملفات أخرى.

### التقييم الأمني

هذا الإصلاح يزيل تحذيرات CSS المتوقعة، لكنه يخفف حماية CSS من الحقن. الحل الأمني النهائي هو نقل كتل `<style>` إلى ملفات static، استبدال خصائص `style` بأصناف CSS، ثم حذف استثناءات `unsafe-inline` وتفعيل CSP بدل Report-Only بعد مراجعة السجلات.

### ملاحظات الأداء

زمن الاستجابة مرتفع ومتذبذب نسبيًا، خصوصًا لنقاط النظام المحمية. نقطة `/api/system_features` وصلت إلى نحو 19.8 ثانية في أسوأ عينة، و`/api/system_metrics` إلى نحو 13.6 ثانية. هذه القياسات تشمل زمن الشبكة وطبقة الاستضافة، ولا تكفي وحدها لإثبات أن قاعدة البيانات أو التطبيق هو مصدر التأخير.

يوصى بتكرار القياس من نفس منطقة الاستضافة، وإضافة request correlation ID وقياس داخلي لزمن handler وdatabase، ثم فحص سجلات 509 أثناء الاختبار. كما ينبغي إبقاء `/health` خفيفًا وغير معتمد على قاعدة البيانات إن كان الغرض منه health check للمنصة.

## فحص أمني للتكوين والبيئة

تم الفحص دون طباعة قيم الأسرار.

### نتائج إيجابية

لم يظهر في النسخة المحلية:

- ملف `.env` فعلي.
- ملفات `.pem` أو `.key` أو مفاتيح خاصة.
- مفاتيح AWS أو Google أو GitHub بصيغ عالية الثقة.
- ملفات credentials أو cookies متتبعة.
- قيم اعتماد حقيقية في `.env.example`؛ القيم الموجودة placeholders.

تم كذلك تنفيذ `git diff --check` ونجح، كما نجح فحص ترجمة Python للملفات المستهدفة.

### مخاطر متبقية

1. **سر مؤقت عند غياب `SECRET_KEY`:** الكود يولد مفتاحًا عشوائيًا عند غياب المتغير، ما يؤدي إلى إبطال الجلسات عند إعادة التشغيل. يجب ضبط `SECRET_KEY` ثابت وقوي في بيئة 509 وعدم تسجيل قيمته.
2. **Rate limiting محلي افتراضي:** عند غياب `RATELIMIT_STORAGE_URI` و`REDIS_URL` يستخدم التطبيق `memory://`، ما يجعل الحدود منفصلة لكل worker وغير مناسبة للحماية الموحدة في الإنتاج.
3. **بيانات تشغيلية في مستودع عام:** توجد ملفات مركبات وسائقين وصور فريق وملفات Excel/Word تشغيلية. لا تظهر كمفاتيح تقنية، لكنها قد تحتوي على بيانات شخصية أو تشغيلية ويجب نقلها إلى تخزين خاص أو تنقيتها.
4. **مصادر CDN واسعة:** السياسة تسمح بعدة نطاقات خارجية، لذلك يفضل تثبيت الأصول أو استخدام Subresource Integrity حيثما أمكن.
5. **CSP غير مفعّلة حاليًا:** المتغير `CSP_ENFORCE` يحدد الانتقال إلى header الفعلي، لكن تفعيل enforcement يجب أن يسبقه تنظيف inline CSS وinline JS ومراجعة كاملة للسجلات.

## تحديث: ترحيل CSS وتدقيق التبعيات

تم ترحيل كتل `<style>` وخصائص `style="..."` الثابتة من قوالب المشروع إلى ملفات versioned تحت `static/css/page/`. تم تحويل 1950 خاصية CSS ثابتة، ومعالجة الخصائص الديناميكية المتبقية باستخدام أصناف دلالية وعنصر `progress`. التحقق الحالي يؤكد عدم وجود `<style>` أو `style=` داخل قوالب HTML.

لا يمكن تفعيل CSP enforcement الكامل بعد، لأن المشروع ما زال يحتوي على inline JavaScript وخصائص أحداث مثل `onclick` و`oninput` في القوالب. لذلك أزيلت استثناءات CSS `unsafe-inline` وأصبح CSS محكومًا بسياسة خالية من inline CSS، بينما بقي header العام في وضع Report-Only إلى حين ترحيل JavaScript أو إضافة nonces بطريقة مركزية.
